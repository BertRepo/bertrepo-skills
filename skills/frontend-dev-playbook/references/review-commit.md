# 评审、提交与交接

## 评审聚焦当前 diff

先理解目标与契约，再核查数据流、生命周期、错误/空/加载状态、权限、无障碍和相关测试。指出可复现问题和文件位置，不用大段风格偏好淹没真实缺陷。

把确认的缺陷与待验证风险分开。代码审查不能声称浏览器/接口测试已通过。无需为简单改动强行创建多个子代理；复杂独立模块才值得并行评审。

## Git

沿用团队提交格式。提交前确认暂存文件、敏感信息和临时产物；不回退用户无关改动，不提交临时 Mock 目标和 token。用户要求维护的正式 Mock/开发代理配置应正常交付。只在任务明确授权时 commit/push/PR；授权后的可逆准备工作自行完成。

PR 以最终问题和行为变化开头，写测试结果、迁移影响和材料限制。不要把任务聊天记录充当设计说明。

## 交接最小集

说明变更、验证、启动方式（仅有变化时）、配置/兼容影响、未完成项及 Mock/服务清理记录。

没有相关变更则不强制修改 README、跑全量构建或创建 commit。交付标准是用户目标得到可验证处理，不是检查表被逐项机械打勾。
